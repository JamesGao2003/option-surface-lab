02 / THE FUNCTION

What the script decides, and from what

Same wheel as the backtest, with one change: the put distance is not a fixed 5% any more, it comes from the last twenty days of realised volatility. The whole thing is one standard-library Python file, plan_orders.py, about 150 lines.

01 / READ

Prices and the book

Load price_history.json, the daily bars the course server writes from Interactive Brokers for conid 265598 (Apple). If the newest bar is more than five days old, fill the gap from Stooq's free daily CSV so a server outage does not stop the run. Then load mkt/positions.json, the book Sanji writes after each session. If it does not exist yet, the book is all cash: $50,000.

02 / MEASURE

Volatility and trend

Daily sigma is the standard deviation of the last 20 log returns. Weekly sigma is that times the square root of five. The trend check is the 10-session return. Apple at 1.7% a day gives a weekly sigma near 3.8%.

03 / DECIDE

Flat, long, or waiting

An option still open: do nothing, the wheel waits for expiry. Long 100 or more shares: sell one covered call per 100 shares at the first $5 strike at or above max(last close, cost basis), written as a bare strike so no option chain is needed. Flat: unless the stock fell 8% or more in 10 sessions, sell a cash-secured put 1.3 weekly sigmas below tomorrow's open, clamped to 3% to 10%, as many contracts as the cash fully covers, max two.

04 / WRITE

One Sanji order

Expiry is the Friday of that week if it is at least three days out, else next Friday, moved to Thursday on a holiday. Limit at the mid of the resolved contract at the open. The id carries the session date so Sanji never fills the same order twice. The file is written to the repo root and to mkt/, and the run log and order history are updated for this page.

WHY 1.3 SIGMAS

The backtest's 5% was really a vol number

In the Amazon backtest a fixed 5% worked out to a bit over one weekly sigma, and it got assigned once in 26 weeks. Hard-coding 5% on a different stock would be a different trade: Apple has been calmer than Amazon this autumn. Scaling the distance by realised sigma keeps the assignment rate roughly where the backtest had it. The 3% floor keeps the premium worth the fee; the 10% cap stops the rule from hiding during a panic, since the crash filter already handles that.

WHAT IT DOES NOT DO

No chain, no Greeks, no guessing

The script never looks at an option chain. Every token it writes is one Sanji can resolve from strikes and the open alone: pct:-N, a bare strike, a date, mid. It does not use delta or premium, which Sanji rejects until Robin has a chain snapshot. It does not edit positions.json, ever. And it does not roll or buy back, same as the backtest.

05 / WHY THIS ALGORITHM

Closing the loop on the semester

Because it is tested

The covered call, the poor man's covered call and the wheel were the three income strategies this course built. The wheel backtest on Amazon had the smallest drawdown and the best Sharpe of the three. Running the one I understand best, with the rules I already wrote down, is the honest choice for a live loop.

Because Sanji can resolve it

The wheel only needs tokens Sanji supports today: a percent-of-open strike, a bare strike, a date expiry, a mid limit. A delta-targeted or premium-targeted version would be rejected until the chain snapshot exists, and an order that is rejected every night is not an algorithm.

What would change next

When fills start, the run log will show the real book and the covered-call branch will get exercised. After that: use the chain snapshot for a delta:15 strike instead of the sigma proxy, and add a second name so the cash is not idle while one put is open. Both are one-line changes in the config block.
